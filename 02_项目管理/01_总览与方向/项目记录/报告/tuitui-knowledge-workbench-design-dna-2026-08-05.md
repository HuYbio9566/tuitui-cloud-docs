# 推推知识工作台典型页面 Design DNA 补充报告

## 给老板的结论

你补充的 6 张截图证明：知识库不是一个孤立的“知识库列表”，而是一套统一的 AI 企业知识工作台。它的主要入口是：

新任务（做事） → 知识库（找资料） → 技能（调用能力） → 专家（找智能体） → 连接器（接外部工具） → 云盘（找文件）。

这几个入口共用同一套页面骨架、顶部导航、左侧历史和内容区操作逻辑。云文档第三次升级必须把它当成“统一工作台”来设计，不能只复制知识库卡片。

## 2. 统一页面骨架

所有截图都出现相同的产品级结构：

1. 最左侧为全局导航：消息、通讯录、项目、广场、团队、连接云、云文档、知识库、云盘、更多。
2. 其右为知识工作台侧栏：新任务、知识库、技能、专家、连接器、云盘、更多、历史。
3. 中央是当前模块内容区。
4. 左侧下方/历史区保留任务记录，例如“任务命名测试”“请帮我撰写一份正式的通知”。
5. 当前模块通过浅蓝选中背景和深色图标/文字表达，不靠大标题或装饰。

因此，新任务/知识库/技能/专家/连接器/云盘应该视为同一个 WorkbenchShell 下的六种工作模式。

## 3. 六个入口分别是什么

### 新任务：从目标开始

新任务页的主视觉是一个非常大的、低装饰的输入工作区。用户可以在对话模式、任务模式、写作模式之间切换；下方有“告诉我想做什么，我来执行任务，@指定知识，/调用技能”的输入提示。

它的产品含义是：用户不需要先理解文件夹和技术概念，可以先说目标，再选择知识和技能。

设计规则：输入区必须是主角；模式切换不能藏起来；@指定知识 和 /调用技能 是可发现的快捷入口；推荐任务卡片只能辅助，不能压过输入器。

### 知识库：按范围找可信资料

知识库页同时支持“我的知识库 / 知识广场”、我创建的 / 我加入的、文档库类型、文档预览、来源、更新时间、文档数量和搜索。

截图中出现的卡片已有轻量文档预览，例如 qskillhub cli.docx、qihoo sso cli.docx、API 对接文档.docx。这说明知识库卡片不是纯宣传卡片，而是“可判断内容质量的目录单元”。

设计规则：卡片/列表要让用户判断“这是什么、来自哪里、最近是否更新、里面有几份文档”；加入状态和权限不能隐藏。

### 技能：按能力找工具

技能页采用“官方技能 / 企业技能 / 我的技能”三层分类，并有“推荐精选”标识。卡片包含图标、技能名称、简介、分类和搜索入口。

设计规则：技能卡片的第一信息是“能帮我做什么”，第二信息是来源/归属，第三信息是使用状态；避免把技能页做成开发者市场。

### 专家：按角色找智能体

专家页在目录之前增加轻量数据看板：近 7 天、使用次数、回答采纳数量、较上周变化。下面是推荐专家和领域分类，例如办公提效、售前咨询、产品研发、项目管理、客户支持。

设计规则：数据看板只服务发现和信任，不要做成复杂 BI；专家卡片必须说明角色、用途、使用人数/版本归属；“+ 创建智能体”是明确的主动作。

### 连接器：按外部系统接入能力

连接器页用一句话说明价值：“连接常用的应用，帮你跨工具获取信息并完成任务”。每个连接器显示配置说明和 API KEY 获取说明。

设计规则：连接器页要把“连接什么、能做什么、需要什么权限/密钥、是否已配置”一次讲清楚；API KEY 是高风险信息，界面必须可隐藏、复制、重新配置和撤销。

### 云盘：按文件和目录找材料

云盘页与知识工作台同壳，但内容区采用更传统的文件管理器：搜索框、全部文件、新建、上传、面包屑、目录树、文件表格、修改时间/修改人/大小。

设计规则：云盘保留文件管理器心智，不要强行卡片化；云盘和知识库通过“引用/加入知识库/在任务中使用”连接，而不是互相替代。

## 4. 统一组件规范

| 组件 | 截图表现 | 第三次升级建议 |
|---|---|---|
| 全局导航 | 10 个固定产品入口 | 固定宽度、图标+文字、浅蓝 active，禁止模块自行改变导航关系 |
| 工作台侧栏 | 6 个主要工作入口 + 历史 | 使用统一 WorkbenchSidebar，只切换内容，不重建壳 |
| 顶部标题 | 统一“360 AI 企业知识库”品牌和当前模块 | 品牌/当前模块/范围层级固定 |
| Tab | 我的知识库/知识广场、官方/企业/我的技能等 | Tab 只表达范围，不混用按钮语义 |
| 搜索框 | 搜索知识库、搜索技能、搜索连接器、输入并搜索文件 | 统一 SearchInput，placeholder 随模块变化 |
| 卡片 | 知识库、技能、专家、连接器 | 统一白底、轻边界、8-12px 圆角；信息字段按模块变体排列 |
| 文件列表 | 云盘文件、目录与元信息 | 用平面行/表格，不用卡片墙 |
| 状态标签 | 已加入、推荐精选、使用人数、更新时间 | 用语义标签，不把所有状态做成彩色胶囊 |
| 主动作 | 新建、上传、创建智能体、配置 | 每个页面只保留一个视觉主动作 |
| 历史 | 左侧任务历史 | 历史是跨模块连续上下文，不因切换入口而消失 |

## 5. 交互关系

新任务
  ├─ @ 指定知识 → 选择知识库/文档范围
  ├─ / 调用技能 → 选择技能
  ├─ 工作空间 → 选择文件夹/来源
  └─ 执行 → 结果可引用知识、技能和连接器

知识库 ──加入/打开──→ 文档范围 ──在任务中使用──→ 新任务
技能   ──调用──────→ 新任务
专家   ──使用──────→ 新任务
连接器 ──授权──────→ 新任务
云盘   ──选择/引用──→ 新任务或知识库

核心原则：这些入口不是 6 个孤立页面，而是一个“目标 → 知识 → 能力 → 外部工具 → 文件 → 执行”的闭环。

## 6. 视觉与品牌气质

- 气质：冷静、企业级、可信、效率导向、克制。
- 视觉重点：信息层级、状态、来源、范围和可执行动作，而不是插画和装饰。
- 图片语言：功能图标、文件类型图标、专家头像/身份标记、小尺寸文档缩略图；不依赖大照片或营销插画。
- 动效：只为 active、hover、打开面板、加载和反馈服务；不建议加入粒子、3D、玻璃和背景动画。
- 品牌语气：直接、实用、少口号；按钮用“新建 / 上传 / 创建智能体 / 配置 / 使用”等动词。

## 7. 开发信息反推

建议前端组件分层：

WorkbenchShell
├─ GlobalRail
├─ WorkbenchSidebar
│  ├─ WorkbenchNavItem
│  └─ HistoryList
├─ WorkbenchHeader
└─ ModuleRenderer
   ├─ NewTaskModule
   ├─ KnowledgeModule
   ├─ SkillsModule
   ├─ ExpertsModule
   ├─ ConnectorsModule
   └─ CloudDriveModule

建议统一数据接口：

ModuleNavItem: id, label, icon, active, permission
ResourceCard: id, title, type, description, source, updatedAt, usageCount, status
TaskContext: knowledgeIds[], documentIds[], skillIds[], expertId, connectorIds[], driveFileIds[]
PermissionState: visible, canUse, canEdit, canConfigure, reason

建议每个页面都提供 5 类状态：加载中、空状态、有内容、权限不足、操作失败。连接器再增加“未配置 / 已配置 / 过期 / 撤销”状态；知识库再增加“未加入 / 已加入”；技能和专家增加“可用 / 已停用”。

## 8. 对云文档第三次升级的硬约束

1. 不要只做知识库列表；必须把新任务、技能、专家、连接器、云盘作为统一工作台的邻接入口保留。
2. 不要为每个模块设计一套不同的颜色、圆角、导航或搜索框。
3. 不要把云盘表格卡片化，不要把专家数据看板做成重型 BI。
4. 不要让“@指定知识”和“/调用技能”成为隐藏功能；它们是新任务页的核心交互语言。
5. 不要把来源、更新时间、使用人数、权限和配置状态藏在二级页面。
6. 不要让连接器 API KEY 明文常驻页面；必须有掩码、复制、重新配置和撤销。
